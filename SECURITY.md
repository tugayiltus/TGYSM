# Security Policy

## Supported versions

| Version | Supported |
|---|---|
| `master` (first release, Phase 6) | Yes |

## Reporting a vulnerability

Report privately to the project owner, Tugay İLTUŞ (GitHub [@tugayiltus](https://github.com/tugayiltus)), through a private GitHub security advisory. Do not open a public issue. Include affected endpoint or screen, steps to reproduce, impact, and any proof of concept. Acknowledgement target: 5 business days.

## Security posture

- **Authentication:** local accounts only; PBKDF2 password hashing (`PasswordHasher<T>`); 12–128 character passwords with letters and digits; forced change of temporary passwords; lockout after 5 failures for 15 minutes; per-IP login rate limit; uniform `auth.invalid_credentials` response (ADR-0004).
- **Sessions:** `__Host-tgysm` cookie (`Secure`, `HttpOnly`, `SameSite=Strict`); every request re-validates active status and security stamp; role change, deactivation and password reset end sessions.
- **CSRF:** antiforgery token in `X-CSRF-TOKEN` on every unsafe API request.
- **Authorization:** server-side policies; `/api/v1/admin/*` requires the admin role; hidden UI is not treated as authorization (ADR-0005).
- **Audit:** security and admin events in append-only `audit_events` (database trigger); passwords, hashes and tokens are never logged or audited.
- **Email:** the SMTP password (`Email:Smtp:Password`) comes from user-secrets or the environment only, never `appsettings`; it is not logged, audited or stored. Send errors are sanitized before they are stored in `email_deliveries.last_error` (credential-shaped pairs redacted, cut to 500 characters). Templates are plain text with a fixed per-event variable allow-list and no expression evaluation, so there is no markup or template injection surface (ADR-0016). `App:PublicBaseUrl` must be an absolute `http`/`https` URL or the hosts refuse to start, so links in email never render as relative paths.
- **Account-link tokens in email:** the token is kept only as a Data Protection–encrypted `notification_outbox.protected_secret`, rendered into the body at send time, and cleared (delivery body becomes `[cleared]`) once the delivery is `sent` or terminally `failed` (ADR-0015). Outbox payloads hold ids and reason codes only, never subject or resolution text. Set-password links are covered under "Password set links" below.
- **Password set links (ADR-0017):** tokens are 32 random bytes; only a hash is stored (`password_tokens.token_hash`), the token exists only in the email. Activation links last 72 hours and reset links 1 hour; each works once, redemption is a single conditional update, so parallel use has one winner. Every invalid, used or expired token gives the same `auth.token_invalid`. Redeeming a link sets the password, rotates the security stamp (ends other sessions) and voids the user's other unused links; unused links are also revoked when an admin changes the user's email address or issues a temporary password, and an account email queued before an address change is never sent to the new address. `POST /auth/forgot-password` answers 202 and does the same work on the request path for any address (the Worker looks the account up later), so timing and response do not reveal whether an account exists; the address is kept in an outbox event for at most 30 days (`Cleanup`). While an account has an unused reset link younger than 15 minutes, further requests are skipped (no new link, no email). `POST /auth/forgot-password` and `POST /auth/set-password` have per-client-IP rate limits (`Security:ForgotPasswordPermitLimitPerMinute`, `Security:SetPasswordPermitLimitPerMinute`, default 5 each). An admin retry of a failed account email issues a new link and revokes the older ones.
- **Data Protection keys (ADR-0024, closes the earlier known gap):** `AddDataProtection()` uses the shared application name `Tgysm` and, outside Development, persists the key ring to `DataProtection:KeysPath` (required; the API and the Worker refuse to start when it is empty or not writable). In Docker it is the `keys` volume at `/data/keys`, mode 0700, owned by the non-root `app` user, shared by `api` and `worker`, and included in every backup. The keys are stored unencrypted at rest (the framework warns at startup): protection is the folder permission plus restricted access to the host and the backups. Encrypting the key ring with a certificate is not configured (one more secret to issue, rotate and back up; ADR-0024 Alternative 4) and stays an option for an operator who needs it. Anyone who can read the keys volume or a backup archive can unprotect account-link tokens until they expire (72 h activation, 1 h reset). Losing the keys signs every user out and makes pending account-link emails unrenderable (`docs/operations.md`).
- **Worker:** `Tgysm.Worker` has no network listener and no signed-in user; its audit rows carry a generated correlation id and no user id. It needs the database connection string and, for SMTP, the secret above, through environment or user-secrets.
- **Health probe:** `GET /api/v1/health` is anonymous and returns only `{ status }` (`ok` or `degraded`); job names, timestamps and errors are available only to admins at `/api/v1/admin/system/workers`.
- **Knowledge base (ADR-0019):** employees see only `published` articles with `employees` visibility; every other article is 404 on list, detail, search and ticket links, so its existence is not revealed. Create, edit, status actions and revisions need IT staff or admin. The server refuses a public ticket reply that links an `internal` article (`knowledge.internal_article_in_public_reply`); the UI picker is not the guard. Article Markdown is rendered in the browser by `react-markdown` without raw HTML (`rehype-raw` is not used), and links carry `rel="noopener noreferrer"`. Enabling raw HTML would need a sanitiser and a new ADR. Search input is matched with `LIKE` and its `%`, `_` and `\` are escaped (`LikePattern`), so user text cannot act as a wildcard.
- **Reports and export (ADR-0020):** `/api/v1/reports/*` need IT staff or admin (employees 403). Admins see all tickets, IT staff only tickets whose current team is one of theirs; figure, drill-down and export share one scoped query, so a file never holds rows the viewer cannot see. Each export writes a `reports.exported` audit row naming report, metric, bucket, part and filter, never the exported rows. Excel cells are written as text or numbers, never formulas, so ticket text such as `=cmd(...)` is not evaluated when the file is opened. The synchronous export is capped at 5,000 rows (409 `reports.export_too_large`).
- **Background exports (ADR-0020):** a job is built by the Worker under the creator's scope at run time; a creator who is inactive or no longer IT staff or admin by then fails the job without a file. Download (`GET /api/v1/reports/exports/{id}/download`) re-checks on every request that the caller is the job's creator, is still active, still has the IT staff or admin role, and that the file is inside its 24-hour lifetime; any other caller or a failed job gets 404 (so a job id reveals nothing), an expired file 410. Responses carry `X-Content-Type-Options: nosniff`. Requests and downloads are audited (`reports.export_requested`, `reports.export_downloaded`). Limits bound resource use: 100,000 rows per job, 3 pending or running jobs per user, 3 runs per job; stored errors are sanitized (no credentials or row data). Expired files are deleted by `Cleanup`.
- **Device catalog and asset tags (ADR-0023):** catalog writes (`/api/v1/admin/brands`, `/api/v1/admin/models`) need `admin` and are audited; `GET /api/v1/assets/catalog` needs IT staff or admin and returns only active entries. Asset tags are generated by the server from a database sequence; a client cannot choose one, and CSV legacy tags with the reserved `DMR-` prefix are refused. A new incident may link only a device actively assigned to its requester.
- **File store:** attachments and export files live on local disk under `Files:RootPath`, outside the web root, named by random 32-character hex keys; any other key is refused, so a key cannot point outside the root. Outside Development the root must be set explicitly (startup fails otherwise) and shared by the API and the Worker; restrict the folder to the service account.
- **Transport:** HTTPS required in production. nginx terminates TLS (TLS 1.2 and 1.3 only) with the company certificate from `deploy/certs/` (git-ignored, mounted read-only) and redirects HTTP to HTTPS; the API adds HSTS and HTTPS redirection outside Development/Testing.
- **Proxy trust (ADR-0024):** outside Development the API applies `X-Forwarded-For` and `X-Forwarded-Proto` only from the networks in `Http:KnownProxyNetworks` (CIDR; compose passes the internal subnet `TGYSM_SUBNET`); an invalid entry stops startup. Forwarded headers from any other address are ignored, so a client cannot spoof its address to the login rate limit or claim HTTPS. In Development only the loopback Vite proxy is trusted for `X-Forwarded-Proto`. A wrong `TGYSM_SUBNET` makes sign-in fail (the antiforgery cookie needs HTTPS) rather than trusting too much.
- **Containers:** `tgysm-api` and `tgysm-worker` run as the non-root `app` user (uid 1654) on `mcr.microsoft.com/dotnet/aspnet:10.0`; no secret is baked into any image layer, and `.dockerignore` keeps `.env` and build output out of the build context. PostgreSQL is not published to the host; only nginx listens on host ports.
- **Backups (ADR-0025):** archives hold the database dump, the file store and the key ring; they are written with mode 600 (`umask 077`), also the safety backup `tools/restore.sh --force` takes first. The manifest records the SHA-256 of `db.dump` (`dbSha256`); restore refuses an archive whose dump does not match it, or that has no checksum. Keep `BACKUP_HOST_DIR` and every off-host copy access-restricted.
- **Secrets:** no credentials, keys or connection strings in the repository. Production secrets (`POSTGRES_PASSWORD`, `SMTP_PASSWORD`) live only in `deploy/.env` on the host (git-ignored; `deploy/.env.example` lists every key with placeholder values; keep it mode 600) and reach the containers as environment variables. Certificates and keys in `deploy/certs/` are git-ignored. Development connection strings live in `dotnet user-secrets`; tests read `TGYSM_TEST_ADMIN_CONNECTION`; CI uses a throw-away database password for its service container.
- **Dependencies:** versions pinned centrally (`backend/Directory.Packages.props`, `frontend/package-lock.json`).

## Dependency & supply chain

- Automated update tool: Dependabot (`.github/dependabot.yml`), weekly for `nuget` (`/backend`), `npm` (`/frontend`), `docker` (`/`, base images) and `github-actions` (`/`); minor and patch updates grouped per ecosystem. `eslint` and `@eslint/js` are held below 10 until `eslint-plugin-react`, `eslint-plugin-jsx-a11y` and `eslint-plugin-import` support ESLint 10.
- CI gate: `.github/workflows/ci.yml` runs on every push and pull request (lint, tests with coverage gates, E2E, both image builds); the workflow has read-only `contents` permission.
- Each bump must pass `tools/lint.sh`, `tools/test.sh` and `tools/e2e.sh` (the CI run) before merge.
- Major version bumps additionally get a manual smoke test of login, forced password change and `/admin/users`.
